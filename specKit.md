# Spec Kit

A step-by-step guide to installing and initialising [Spec Kit](https://github.com/github/spec-kit) — a CLI for spec-driven development with optional AI agent integrations.

---

## Prerequisites

Spec Kit is distributed via [uv](https://github.com/astral-sh/uv), a fast Python package manager.

### 1. Install uv

```bash
brew install uv
```

Verify the installation:

```bash
uv --version
```

---

## Step 1 — Install Spec Kit CLI

```bash
uv tool install specify-cli
```

> This installs the `specify` command globally via uv's tool layer.

---

## Step 2 — Initialise a Project

### Basic init (no agent integration)

```bash
specify init my-project
cd my-project
```

### Init with an agent integration

Pass `--integration` to wire up an AI agent at init time:

```bash
# GitHub Copilot
specify init my-project --integration copilot

# Cline
specify init my-project --integration cline

cd my-project
```

> The `--integration` flag generates the agent-specific configuration files alongside the standard spec structure.

---

## Step 3 — Install an Agent Integration (if not done at init)

If you initialised without `--integration`, or if the integration did not apply correctly, run the following from inside your project directory:

```bash
cd my-project
specify integration install copilot
```

### Verify the integration files were created

List hidden files to confirm the agent configuration was written:

```bash
ls -a
```

You should see integration-specific files such as `.github/` (Copilot) or `.clinerules` (Cline) alongside the standard spec files.

---

## Step 4 — Init into an Existing Directory

To initialise Spec Kit inside a directory that already exists (without creating a new subdirectory), use `.` as the target:

```bash
cd my-project2
specify init .
```

Then install the agent integration:

```bash
specify integration install copilot
```

Confirm all files were written:

```bash
ls -a
```

---

## Step 5 — Create the Constitution

The **constitution** is a foundational document that defines the permanent engineering standards for your project — architecture rules, coding conventions, security requirements, testing strategy, and more. Every feature generated by Spec Kit will automatically follow these standards.

The constitution is stored inside your project under:

```text
.specify/memory
```

### How to generate the constitution

You have two options:

#### Option A — Ask your AI agent to generate a prompt

Ask your AI agent (Copilot, Cline, etc.) to create a constitution prompt tailored to your project, then follow Option B with the output.

#### Option B — Use an existing prompt file

If you already have a constitution prompt file (e.g. `speckit-constitution-prompt.txt`), pass its contents directly to Spec Kit via the slash command inside your agent:

```text
/speckit.constitution <paste the output from the prompt or file here>
```

The agent reads the pasted content and scaffolds the `.specify/memory` constitution for your project.

### General rule

1. Prepare your prompt — either generate one with AI or use an existing file.
2. Run `/speckit.constitution` with the prompt output pasted in.
3. Review the generated constitution in `.specify/memory`.
4. Iterate: refine the prompt and re-run until the constitution matches your standards.

> A well-formed constitution covers: technology stack, architecture principles, API design standards, clean code rules, security requirements, testing strategy, observability, and deployment conventions.

---

## Step 6 — Manage Features (one at a time)

Spec Kit is designed around building **one feature at a time**. Each feature goes through its own specify → clarify → plan → implement cycle.

### Optional — Install the Git extension

The Git extension automatically creates a feature branch for each new feature:

```bash
specify extension add git
```

Verify it is installed:

```bash
specify extension list
```

---

## Step 7 — Write the Feature Specification

Focus on **what** you want to build, not how. Describe the feature in plain language — Spec Kit translates it into a structured specification.

```text
/speckit.specify <user registration with email and password — add as much information as you can regarding those user stories>
```

```text
/speckit.specify <user login with email and password>
```

> Spec Kit tracks the active feature in `.specify/feature.json`. This file tells Spec Kit which feature all subsequent commands apply to.

---

## Step 8 — Clarify the Specification (optional but recommended)

Review the generated specification, confirm it is correct, and close any gaps before moving to planning.

```text
/speckit.clarify
```

Focus on a specific concern:

```text
/speckit.clarify <focus on security>
```

Answer all questions raised by the agent. Repeat until the specification is complete and unambiguous.

---

## Step 9 — Plan the Implementation

Spec Kit reads the specification and converts it into a technical plan — architecture decisions, component breakdown, and implementation approach.

```text
/speckit.plan <technical approach>
```

> You may paste the contents of an existing plan file as the argument to guide the output.

---

## Step 10 — Generate a Requirements Checklist (optional)

Produces a quality checklist from the specification document — think of this as a unit test for your requirements. The specification is **read only**; it is not modified.

```text
/speckit.checklist
```

After reviewing the checklist:

1. Update the specification file to address any gaps found.
2. Re-run `/speckit.clarify` and answer any new questions.
3. Re-run `/speckit.checklist` to confirm all items pass.

---

## Step 11 — Generate Implementation Tasks

Reads the specification, plan, and any research or quickstart files to produce a complete, ordered task list.

```text
/speckit.tasks
```

> Spec Kit auto-detects the active feature folder from `.specify/feature.json` to scope the task list correctly.

---

## Step 12 — Analyse for Inconsistencies (optional)

A read-only pre-flight check. Compares the specification, plan, and task list and reports any mismatches or incomplete areas before any code is written.

```text
/speckit.analyze
```

Review the report and resolve any inconsistencies before proceeding to implementation.

---

## Step 13 — Implement the Feature

Spec Kit builds the feature task by task, following the plan and constitution.

```text
/speckit.implement
```

Once implementation is complete, run the application to verify:

```bash
mvn spring-boot:run
```

---

## Step 14 — Converge (optional)

Compares what was implemented against the specification, plan, and task list. Use this to catch any drift between intention and implementation.

```text
/speckit.converge
```

> Converge may update the task list. If it does, re-run `/speckit.implement` then `/speckit.converge` again. Repeat until you get a final, clean convergence check with no outstanding items.

---

## Using Two LLMs Together — Planning with Claude, Implementation with GLM

Spec Kit is LLM-agnostic. Because every phase produces a **written artefact** (constitution, specification, plan, task list), you can use a different model for each phase. A particularly effective split is:

| Phase | Model | Why |
| --- | --- | --- |
| Constitution, Specify, Clarify, Plan, Checklist | **Claude** (Claude Code) | Strong at long-form reasoning, structured documents, and surfacing edge cases |
| Tasks, Implement, Converge | **GLM** (z.ai) | Fast, efficient code generation that follows an existing written plan |

The written artefacts are the handoff boundary. Claude thinks and writes; GLM reads and builds.

---

### How it works in practice

#### Phase 1 — Open Claude Code in your project

Claude Code runs in the terminal and reads your project files directly. All Spec Kit slash commands are available inside Claude Code.

```bash
# open Claude Code in the project root
claude
```

#### Phase 2 — Run all planning phases in Claude

Use Claude for everything up to and including task generation:

```text
# 1. Generate the constitution (once per project)
/speckit.constitution <paste your constitution prompt>

# 2. Specify the feature
/speckit.specify <your feature requirements>

# 3. Close gaps (optional but recommended)
/speckit.clarify

# 4. Generate the technical plan
/speckit.plan <your implementation notes>

# 5. Quality-check the requirements (optional)
/speckit.checklist

# 6. Generate the ordered task list
/speckit.tasks
```

At this point `.specify/features/<feature-name>/` contains:

- `spec.md` — the structured specification
- `plan.md` — the technical implementation plan
- `tasks.md` — the ordered, granular task list

These files are the contract Claude hands to GLM.

#### Phase 3 — Exit Claude Code, open GLM (z.ai)

Open the [z.ai](https://z.ai) web interface or the GLM desktop client and point it at the same project directory (or paste the relevant files into context).

#### Phase 4 — Run implementation phases in GLM

Provide GLM with the context it needs and run the implementation commands:

```text
# Paste or attach the contents of:
#   .specify/memory/         ← constitution
#   .specify/features/<name>/spec.md
#   .specify/features/<name>/plan.md
#   .specify/features/<name>/tasks.md

# Then run:
/speckit.implement
```

GLM reads the task list and builds the feature task by task, following the plan and constitution that Claude authored.

#### Phase 5 — Verify convergence

Run convergence in either model. Claude is better at spotting spec drift; GLM is faster at confirming mechanical task completion:

```text
/speckit.converge
```

If converge reports outstanding items, re-run `/speckit.implement` then `/speckit.converge` until the check is clean.

---

### Decision guide — which model for which task

```text
Claude (Claude Code)                    GLM (z.ai)
─────────────────────────────           ──────────────────────────
/speckit.constitution                   /speckit.implement
/speckit.specify                        /speckit.converge  (optional)
/speckit.clarify
/speckit.plan
/speckit.checklist    (optional)
/speckit.tasks
/speckit.analyze      (optional)
```

---

### Tips for a clean handoff

1. **Finish all clarification in Claude before switching.** Once you move to GLM, the spec is frozen. Do not clarify or re-specify mid-implementation — it breaks GLM's task context.
2. **Pass the full constitution to GLM, not just the plan.** GLM needs the engineering standards to make the right micro-decisions while coding.
3. **Use `/speckit.analyze` in Claude before switching.** This catches spec-vs-plan mismatches before GLM touches any code.
4. **Keep the task list as the handoff signal.** When `.specify/features/<name>/tasks.md` exists and looks correct, you are ready to switch to GLM.
5. **Run the test suite after each GLM implement cycle.** GLM follows the plan faithfully, but tests are the objective check that the output matches intent.

---

### Why this split works well

Claude excels at **understanding and structuring** — it interrogates requirements, spots unstated assumptions, and produces well-reasoned plans. GLM excels at **executing** — it reads a concrete plan and generates accurate, fast code. Spec Kit's written artefacts are precisely the interface that makes this handoff reliable: there is no ambiguity passed between models, only structured documents.

## Feature Development Cycle

```text
specify  →  Write WHAT to build         (/speckit.specify)
clarify  →  Close the gaps              (/speckit.clarify)       [optional]
plan     →  Convert to HOW              (/speckit.plan)
checklist →  Unit-test the requirements (/speckit.checklist)     [optional]
tasks    →  Generate implementation tasks (/speckit.tasks)
analyze  →  Pre-flight consistency check (/speckit.analyze)      [optional]
implement →  Build task by task         (/speckit.implement)
converge →  Verify & reconcile          (/speckit.converge)      [optional]
```
